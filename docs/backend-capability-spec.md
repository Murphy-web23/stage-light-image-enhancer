# Backend Capability & Frontend Requirement Specification

> 分析對象：`api.py`、`src/pipeline.py`、`src/enhancement.py`、`src/color_correction.py`、`src/superres.py`、`src/utils.py`。
> 目前前端（`web/`）僅用來確認「這個 API 實際上是怎麼被呼叫的」，本文件不描述、不參考、不延續其 UI/UX。

---

## 1. Project Purpose

後端是一個**無登入、無資料庫、單張圖片的影像修復服務**：使用者上傳一張演唱會／舞台燈照片，後端分析色偏並提供一組可調參數，讓前端能即時預覽修復結果，最後輸出原始解析度（可選 2 倍放大）的成品供下載。整個系統沒有帳號、沒有歷史紀錄、沒有多圖批次處理——它是一次性的、單一工作階段（session）內完成的編修工具。

---

## 2. Backend Architecture Overview

- **框架**：FastAPI（`api.py`），單一檔案定義所有路由。
- **狀態儲存**：純記憶體字典 `_sessions: dict[str, ImageSession]`，沒有資料庫、沒有檔案落地儲存、伺服器重啟即全部遺失。
- **Session 生命週期**：
  - 上傳成功後產生一組 `image_id`（`secrets.token_urlsafe(12)`），對應一個 `ImageSession`（同時存原圖 `full` 與縮圖 `preview`，最長邊 1400px）。
  - **TTL 固定 30 分鐘**，從建立時間起算，**存取不會重新計時**（沒有 sliding expiration）。
  - 全站最多同時保留 **24 個 session**；超過時依建立時間逐一淘汰最舊的，**與該 session 是否還在使用無關**。
  - 沒有 per-user 隔離：`image_id` 本身就是唯一憑證，知道它就能存取對應圖片，沒有額外身分驗證。
- **運算模式**：所有端點都是同步阻塞的 HTTP request/response，沒有 WebSocket、沒有背景工作佇列、沒有進度百分比、沒有輪詢端點。使用者體驗上的「即時感」完全來自單次 HTTP 往返夠快，不是伺服器推送。
- **影像處理**：全部集中在 `src/`，用 OpenCV + NumPy + Pillow，CPU 同步運算（無 GPU 依賴、無外部 AI API 呼叫）。
- **AI/ML 元件**：只有一個，`src/superres.py` 用 OpenCV `dnn_superres`（FSRCNN_x2 模型）做 2 倍超解析度放大；模型檔案或 contrib 模組缺失時，**自動降級**成傳統 Lanczos 插值，不會報錯、對前端完全透明。
- **AI/CV 沒有的部分**：沒有人臉偵測、人臉辨識、活體驗證、Mediapipe、攝影機串流、影片處理。這些在後端完全不存在（見第 7 節）。
- **驗證邏輯**：只有輸入驗證（檔案格式、檔案大小、參數範圍），沒有身分或權限驗證。

## 3. Backend Capabilities

以下依「使用者可以完成什麼事情」列出後端目前提供的每一項功能。

### 3.1 上傳照片並取得色偏分析

- **用途**：使用者提供一張照片，開啟一個編修工作階段，並立刻知道系統偵測到的偏色類型與嚴重程度。
- **使用者需提供**：一個檔案（`multipart/form-data`，欄位名 `file`），必須是 JPG 或 PNG，大小 ≤ 20 MB。
- **後端回傳**：
  - `image_id`（字串，之後所有操作都要用它）
  - `width`、`height`（原圖像素尺寸）
  - `detected_mode`（`auto` / `purple` / `yellow` / `red` / `cyan` / `low_light` 之一）
  - `detected_label`（該模式的中文顯示名稱）
  - `detected_strength`（0–100 的整數，偵測到的偏色嚴重程度）
- **成功條件**：檔案非空、≤20MB、可被 Pillow 解析為圖片。
- **失敗條件**：
  - 檔案是空的 → 400
  - 檔案 > 20MB → 413
  - 檔案無法解析成圖片（非圖片、損毀）→ 400
- **是否需要登入**：否。
- **前置條件**：無。
- **下一步**：取得 `image_id` 後，前端應立刻能顯示「修復前」原圖，並可開始請求「修復後」預覽。
- **是否需要等待**：這一步本身就包含色偏分析（同步完成，無額外等待）；沒有「分析中」的中介狀態需要輪詢——回應回來就是最終分析結果。
- **前端是否需要顯示結果**：是，`detected_label` / `detected_strength` 是要讓使用者知道系統判斷成什麼偏色、多嚴重的重要資訊。

### 3.2 取得「修復前」原圖（用於比較）

- **用途**：讓前端有一張「修復前」的圖可以跟修復後的結果做視覺比較，不需要使用者自己保留原始檔案。
- **使用者需提供**：已存在的 `image_id`（路徑參數）。
- **後端回傳**：PNG 圖片二進位內容（`image/png`），這是**縮圖版**（最長邊 1400px），不是原始解析度。
- **成功條件**：`image_id` 存在且未過期。
- **失敗條件**：`image_id` 不存在 / 已過期 / 已被淘汰 → 404，訊息「圖片工作階段已過期，請重新上傳。」
- **是否需要登入**：否。
- **前置條件**：必須先完成 3.1 上傳。
- **下一步**：無自動下一步，純顯示用。

### 3.3 即時預覽修復結果

- **用途**：使用者調整任何修復參數後，取得**縮圖版**（最長邊 1400px）的修復結果，用於快速的互動預覽，不用等原始解析度運算。
- **使用者需提供**：`image_id`（路徑參數）+ 完整的修復參數 JSON（見第 9 節「Input」）。
- **後端回傳**：PNG 圖片二進位內容。
- **成功條件**：`image_id` 有效、`mode` 是合法值、其餘參數在允許範圍內。
- **失敗條件**：
  - `image_id` 過期/不存在 → 404
  - `mode` 不在 `{auto, purple, yellow, red, cyan, low_light}` 內 → 400
  - 其他參數超出 Pydantic 定義的範圍（例如 `brightness` 給 200）→ FastAPI 自動回傳 422 驗證錯誤
  - 處理過程中發生 `ValueError`（目前程式碼中主要就是不支援的 mode）→ 400
- **是否需要登入**：否。
- **前置條件**：必須已有 `image_id`。
- **下一步**：無自動下一步；使用者可以繼續調參數（重複呼叫這個端點）或進到 3.4 下載。
- **是否需要等待 / 即時狀態**：每次呼叫都是一次同步運算（依圖片大小與參數約零點幾秒到數秒），沒有進度回報，前端只能自行決定要不要顯示 loading 提示、要不要對頻繁的參數變動做防抖（debounce）或忽略中途結果。**注意**：`upscale_2x` 參數在 preview 端點會被忽略效果（因為預覽本來就是縮圖），呼叫端不需要因為這個參數變動而重新預覽。

### 3.4 輸出原始解析度成品（供下載）

- **用途**：用同一組參數，對**原始解析度**圖片跑一次完整修復流程，產出可下載的最終檔案；可選擇是否做 2 倍超解析度放大。
- **使用者需提供**：`image_id` + 完整修復參數 JSON（與 3.3 相同的 schema，多了 `upscale_2x` 才會真正生效）。
- **後端回傳**：PNG 圖片二進位內容（原始解析度，或 `upscale_2x=true` 時為 2 倍寬高）。
- **成功條件**：同 3.3。
- **失敗條件**：同 3.3。
- **是否需要登入**：否。
- **前置條件**：必須已有 `image_id`；概念上通常會先用 3.3 調好參數,再呼叫這個端點做最終輸出（但後端不強制順序，也可以不呼叫 3.3 直接呼叫這個）。
- **下一步**：拿到 PNG bytes 後，「下載」這個動作（存成檔案）完全是前端行為，後端不知道使用者有沒有真的存檔。
- **是否需要等待**：**這是整個系統中耗時最長的操作**——原始解析度全流程運算 + 可選的 2× tiled 超解析度模型推論。沒有進度百分比，是單一個可能耗時數秒的同步請求，前端必須要有明確的「處理中」狀態，不能讓使用者以為沒反應。

### 3.5 查詢部署環境能力

- **用途**：讓前端知道「這個部署環境是否真的有安裝超解析度模型」，才能誠實地告訴使用者 2× 放大會用 AI 模型還是傳統插值。
- **使用者需提供**：無。
- **後端回傳**：`{"superres": true/false}`。
- **成功條件**：永遠成功（沒有失敗分支）。
- **是否需要登入**：否。
- **前置條件**：無，甚至不需要先上傳圖片，可以在頁面載入時就先查。
- **下一步**：純資訊查詢，不影響任何流程；`upscale_2x=true` 這個放大選項在後端**永遠可用**（沒有模型時自動降級成 Lanczos 插值），這個端點只是告知放大品質，不是「能不能用」的開關。

## 4. User Actions Required

依照後端實際流程，重新導出「使用者真正需要主動做的操作」：

| 操作 | 是否必要 | 說明 |
|---|---|---|
| 選擇 / 拖入一張圖片檔案 | **必要** | 3.1 的唯一輸入來源，無法省略。 |
| 調整任一修復參數（模式、強度、亮度…） | **必要（但非逐一操作）** | 使用者要能改變 3.3/3.4 的 JSON 內容；具體用滑桿、開關還是其他 UI 元件不在本文件範圍。 |
| 觸發「重新預覽」 | **可由 UI 自動完成，不需要獨立按鈕** | 後端沒有「先送出再等待確認」的語意，任何參數變動都可以直接呼叫 3.3，不需要使用者按「預覽」鍵。 |
| 觸發「輸出/下載」 | **必要，且應該是獨立、明確的動作** | 因為 3.4 耗時明顯更長、且會產生要保存的檔案，不應該跟即時預覽用同一個觸發時機，必須讓使用者清楚知道自己按下的是「產生最終檔案」。 |
| 換一張圖 / 重新開始 | **必要** | 後端沒有「刪除目前 session」的端點，但既然每個 `image_id` 是獨立的，前端重新呼叫 3.1 上傳新檔即可視為「換一張圖」，不需要對應到某個特定後端操作。 |
| 重新整理色偏偵測 | **不需要** | 偵測只發生在上傳當下（3.1），沒有「重新分析」端點；如果要換偵測模式，本質上是使用者手動切換 `mode` 參數，跟 3.3 是同一個操作，不需要獨立功能。 |
| 登入 / 註冊 | **不存在，不要做** | 後端完全沒有帳號系統。 |
| 查看歷史紀錄 / 之前修復過的圖 | **不存在，不要做** | 沒有任何持久化儲存，session 過期即消失，也沒有「列出所有 session」的端點。 |
| 取消進行中的處理 | **後端未提供對應能力，需要確認** | 沒有「取消請求」端點；前端頂多只能在自己這端忽略已過期的回應（這是目前 `app.js` 的 `renderToken` 作法，屬前端自行決定，非後端契約）。 |

**明確不要做的事**（因為對應的後端行為是自動完成、不该由使用者觸發）：
- 不需要「開始分析」按鈕——分析包含在上傳回應裡。
- 不需要「套用設定」按鈕才能看到預覽——參數本來就可以隨改隨送。
- 不需要區分「儲存」與「下載」——後端沒有儲存的概念，只有算出最終圖片這一件事。

## 5. User Flows

### Flow A — 主要修復流程（唯一的核心流程，後端沒有分支情境）

```
開啟頁面
  │
  ▼
（可選、可背景進行）查詢 /api/capabilities，得知超解析度是否可用
  │
  ▼
選擇 / 拖入一張 JPG 或 PNG 圖片
  │
  ▼
呼叫 POST /api/images 上傳
  │
  ├─ 失敗（空檔 / 超過 20MB / 無法解析）→ 顯示錯誤，停留在「尚未上傳」狀態，可重試
  │
  ▼ 成功
取得 image_id、原圖尺寸、偵測到的偏色與強度
  │
  ▼
顯示「修復前」圖（GET /original）
  │
  ▼
以預設參數呼叫 POST /preview，顯示「修復後」縮圖預覽
  │
  ▼
┌────────────── 迴圈：使用者可重複多次 ──────────────┐
│ 調整任一參數（模式 / 強度 / 亮度 / 對比 / 飽和度 /    │
│ CLAHE / 降噪 / 高光修復 / 畫質修復 / 銳化）           │
│   │                                                  │
│   ▼                                                  │
│ 呼叫 POST /preview（帶最新完整參數）                  │
│   │                                                  │
│   ├─ 失敗（mode 不合法 / 參數超出範圍）→ 顯示錯誤      │
│   ▼ 成功                                             │
│ 更新「修復後」預覽圖                                  │
└───────────────────────────────────────────────────┘
  │
  ▼（使用者對結果滿意，決定輸出）
（可選）開啟「輸出放大 2×」
  │
  ▼
呼叫 POST /render（帶最終參數，含 upscale_2x）
  │
  ├─ 失敗 → 顯示錯誤，維持在編輯狀態，可重試
  │
  ▼ 成功
取得原始解析度（或 2 倍）PNG bytes → 前端觸發檔案下載
  │
  ▼
（可選）使用者可以回到迴圈繼續調整、再次輸出，或換下一張圖（回到最上方重新上傳）
```

### Flow B — Session 過期 / 被淘汰（例外情境，仍屬同一系統，需獨立處理）

```
使用者已上傳圖片並停留編輯（例如中途離開超過 30 分鐘，
或伺服器因為其他訪客上傳量大而把這個 session 淘汰）
  │
  ▼
再次呼叫 /original、/preview 或 /render 任一端點
  │
  ▼
收到 404「圖片工作階段已過期，請重新上傳。」
  │
  ▼
前端必須清楚告知使用者「工作階段已失效」，並引導回到 Flow A 最上方重新上傳
（後端沒有任何機制恢復舊 session，之前調整過的參數只能由前端自己在本地記住並重新套用）
```

> 後端目前只有這兩種 Flow。沒有登入、沒有多圖批次、沒有「儲存草稿之後再回來」的情境。

## 6. Required Screens / Pages

以下是根據 Flow A / B 推導出「功能上」必須存在的畫面單元，**不代表版面、視覺或元件設計**：

### 6.1 Upload（上傳入口）
- **目的**：讓使用者提供圖片，是整個系統唯一的入口狀態。
- **使用者要完成**：選擇或拖入一個檔案。
- **必須顯示**：可接受的格式（JPG/PNG）與大小限制（20MB）；如果檔案不符合會在前端本地先擋掉還是交給後端判斷，屬於前端實作細節。
- **使用者操作**：選擇檔案 / 拖放檔案。
- **會呼叫後端**：`POST /api/images`。
- **成功後去哪**：進入 6.2 編輯畫面。
- **失敗後怎麼處理**：停留在此畫面，顯示後端回傳的錯誤訊息（400/413 的 `detail` 文字）。
- **是否需要 Loading**：需要——上傳 + 分析是一次可能有感延遲的請求。

### 6.2 Editor / Compare（編輯與比較）
> 這裡把「參數調整」與「Before/After 比較」視為同一個功能頁面，因為後端的 3.2（原圖）與 3.3（即時預覽）本來就是為了同時存在、互相比較而設計的兩個端點，沒有理由拆成兩頁。
- **目的**：讓使用者一邊調參數一邊立即看到修復後結果，直到滿意為止。
- **使用者要完成**：反覆調整參數、觀察預覽，最終決定輸出。
- **必須顯示**：
  - 修復前圖（來自 3.2）
  - 修復後預覽圖（來自 3.3，隨參數即時更新）
  - 上傳時偵測到的偏色與強度（`detected_label` / `detected_strength`），作為使用者調整 `mode` 的參考資訊
  - 目前的參數狀態（因為這些參數直接對應後端 schema，缺一個都會影響輸出結果，見第 9 節）
- **使用者操作**：修改 `mode`、`correction_strength`、`preserve_stage_light`、`brightness`、`contrast`、`saturation`、`use_clahe`、`use_denoise`、`use_highlight_recovery`（+`highlight_strength`）、`use_quality_restore`（+`quality_strength`）、`use_sharpen`；換圖；觸發輸出。
- **會呼叫後端**：`POST /api/images/{id}/preview`（每次參數變動）、`POST /api/images/{id}/render`（觸發輸出時）。
- **成功後去哪**：輸出成功後可以停留在本頁（後端沒有結果頁的概念，輸出結果就是使用者本機拿到的一個檔案），也可以視前端設計顯示一個「已完成」的確認狀態。
- **失敗後怎麼處理**：
  - 預覽失敗：提示錯誤，但保留使用者已調整的參數值，讓他可以修正後重試（不要清空表單）。
  - 輸出失敗：提示錯誤，回到可編輯狀態，不遺失已上傳的圖片與參數。
  - 404（session 過期）：導向「需要重新上傳」的狀態（對應 Flow B）。
- **是否需要 Loading / Progress**：
  - 預覽：需要一個「處理中」提示，但沒有百分比可顯示（後端不回報進度）。
  - 輸出：**必須**有明顯的處理中狀態，因為這步驟耗時最長；同樣沒有百分比可用。
- **特殊 UI 需求**：因為後端明確定義了「預覽用縮圖」與「輸出用原始解析度」是兩個不同品質的結果，前端有責任讓使用者理解「現在看到的預覽」與「真正下載到的檔案」解析度不同，尤其是 `upscale_2x` 只影響下載檔、不影響預覽（見第 8 節、第 12 節）。

### 6.3 Session-expired（工作階段失效）
- **目的**：明確告知使用者操作失敗的原因是「逾時或被系統淘汰」，而不是一般性錯誤，並提供唯一可行的下一步。
- **使用者要完成**：理解目前的圖片與參數已經無法復原，重新開始。
- **必須顯示**：清楚的失效原因說明；不需要顯示技術性的 `image_id`。
- **使用者操作**：重新上傳（等同回到 6.1）。
- **會呼叫後端**：無（這是前端狀態判斷，實際重新開始會再呼叫 3.1）。
- **是否需要確認**：是否要單獨做一個畫面，或用 Toast/Modal 蓋在 6.2 上面，屬於前端設計選擇，不是後端要求；但「使用者必須清楚知道發生了什麼、並知道只能重新上傳」是後端行為導出的硬性需求。

> 後端沒有 Login、Dashboard、Profile、History、Result（獨立結果頁）對應的資料或端點，**不要**因為常見 app 的慣例而加這些頁面。

## 7. AI / Camera / Real-time Features

### 7.1 目前後端「有」的 AI/CV 功能

**只有一項：2× 超解析度放大（FSRCNN 模型，`src/superres.py`）。**

1. **使用者要做什麼**：在輸出（3.4 `/render`）時勾選/開啟 `upscale_2x`。這是唯一的觸發方式，沒有獨立的「跑 AI」按鈕。
2. **系統正在做什麼**：先跑完整個色偏修正 + 影像增強流程，最後才對結果做 2 倍放大（tile-based 推論，384px tile + 16px overlap）；如果環境沒裝 `dnn_superres` 或模型檔案，**靜默降級**成 Lanczos 傳統插值，前端拿不到「這次是不是真的用了 AI」的即時訊號，只能靠 3.5 `/api/capabilities` 事先查詢部署環境的能力。
3. **使用者需要看到什麼**：
   - 開啟這個選項前：知道它「只影響下載檔案、不影響預覽」（因為 preview 端點固定用縮圖，upscale 對預覽沒有可視效果）。
   - 開啟後、下載前：知道最終輸出的尺寸會變成原始寬高的 2 倍。
   - 處理中：因為 tiled 推論會讓 `/render` 明顯變慢，必須有處理中提示。
4. **使用者什麼時候知道成功**：`/render` 請求正常回傳 PNG bytes（HTTP 200）即代表成功，沒有中介成功訊號。
5. **使用者什麼時候知道失敗**：`/render` 回傳非 2xx（例如 400/404/422），或網路請求本身失敗（timeout、斷線）。
6. **失敗後能不能重試**：可以，是無狀態的請求，重新呼叫 `/render` 即可，不影響 session。
7. **是否需要即時回饋**：沒有進度事件可用，只能是「開始 / 結束」兩態。
8. **是否需要倒數**：不需要，後端沒有任何跟時間相關的等待機制（唯一跟時間有關的是 session 30 分鐘 TTL，但那是背景邏輯，不是使用者主動倒數的體驗）。
9. **是否需要進度顯示**：後端無法提供百分比進度，**只能顯示不定進度（indeterminate）的處理中狀態**，除非前端自己做假的進度估計（不建議，容易誤導使用者）。
10. **是否需要相機畫面上的視覺提示**：不適用，這裡完全沒有相機輸入。

### 7.2 目前後端「沒有」的功能（明確排除，避免誤設計）

- 沒有攝影機拍照 / 即時取景
- 沒有人臉偵測、人臉辨識
- 沒有活體驗證（liveness detection）
- 沒有 MediaPipe 或任何姿態/關鍵點偵測
- 沒有影片或串流輸入
- 沒有背景非同步工作佇列（例如 Celery、任務 ID 查詢）
- 沒有 WebSocket 或 Server-Sent Events
- 沒有任何伺服器端「倒數」機制暴露給前端（30 分鐘 session TTL 是伺服器內部邏輯，後端**不會**主動告知前端「還剩幾分鐘」——沒有對應的欄位或端點）

如果未來想要「倒數提醒使用者 session 快過期」，**這是目前後端做不到的**（沒有任何端點回傳 session 的剩餘時間或建立時間），應列入第 14 節「Open Questions」。

## 8. UI States

依實際程式碼路徑列出，狀態名稱是本文件為了描述而定義的（後端本身沒有這些字串常數，是從行為推導出來的）：

| 狀態 | 觸發時機 | 前端需要讓使用者知道什麼 |
|---|---|---|
| `empty` | 尚未上傳任何圖片 | 這是起始狀態，需要提供上傳入口。 |
| `uploading` | 呼叫 `POST /api/images` 期間 | 正在上傳/分析，尚無結果可看。 |
| `ready` | 上傳成功，取得 `image_id`、偵測結果 | 修復前圖與（首次）修復後預覽都已就緒；偵測到的偏色類型與強度應可見。 |
| `previewing` | 呼叫 `POST /preview` 期間（每次參數變動） | 目前看到的預覽可能不是最新的（如果前端沒有處理併發，舊回應可能覆蓋新回應——這是前端要自行處理的競態問題，不是後端保證）。 |
| `preview_error` | `POST /preview` 回傳非 2xx | 顯示具體錯誤訊息（後端 `detail` 欄位），且不應清空使用者已調整的參數。 |
| `rendering` | 呼叫 `POST /render` 期間 | 這是耗時最長的操作，必須清楚標示「正在產生最終檔案」，且應避免使用者重複觸發（例如按鈕要 disable，目前前端的 `app.js` 也是這樣做）。 |
| `render_error` | `POST /render` 回傳非 2xx | 顯示錯誤，保留在可編輯狀態。 |
| `render_success` | `POST /render` 成功回傳 PNG | 使用者需要明確知道「檔案已經可以下載/已下載」。 |
| `session_expired` | 任何端點回傳 404（`image_id` 不存在） | 必須清楚告知「這個工作階段已失效」而不是當成一般錯誤，並引導重新上傳（見 6.3）。 |
| `validation_failed` | 422（Pydantic 參數驗證失敗，例如型別錯誤或超出範圍） | 理論上只會在前端自己送出不合法參數時發生（例如 UI bug），屬於「不應該讓使用者看到」的防呆情境，但仍需要優雅處理而不是白屏。 |
| `unsupported_mode` | 400，`mode` 不在允許清單內 | 同上，正常 UI 流程下不該發生（因為 `mode` 應該來自固定選項），但後端确实会检查并可能拒絕。 |

**後端沒有** `idle` vs 其他前端框架常見狀態命名的強制對應，也沒有 `pending`（排隊等待）、`retry`（自動重試機制）、`unauthorized`（無驗證系統，不存在此狀態）。這些若要在前端出現，都是前端自行定義的 UX 狀態，並非後端契約的一部分。

## 9. Input & Output Data

### Input（使用者需要提供 / 前端需要送出）

**上傳（3.1）**
- `file`：二進位檔案，`multipart/form-data`，欄位名固定為 `file`。

**修復參數（3.3 / 3.4 共用，JSON body，型別為 `EnhanceParams`）**

| 欄位 | 型別 | 預設值 | 範圍 | 說明 |
|---|---|---|---|---|
| `mode` | string | `"auto"` | `auto`/`purple`/`yellow`/`red`/`cyan`/`low_light` | 修復模式 |
| `correction_strength` | int | 70 | 0–100 | 偏色修正強度 |
| `preserve_stage_light` | int | 10 | 0–100 | 保留原始燈光氛圍比例 |
| `brightness` | int | 0 | -100–100 | 亮度 |
| `contrast` | int | 0 | -100–100 | 對比 |
| `saturation` | int | 0 | -100–100 | 飽和度 |
| `use_clahe` | bool | true | — | 局部對比增強開關 |
| `use_denoise` | bool | false | — | 降噪開關 |
| `use_highlight_recovery` | bool | true | — | 高光修復開關 |
| `highlight_strength` | int | 35 | 0–100 | 高光修復強度（只有開關開啟才有效果） |
| `use_quality_restore` | bool | true | — | 畫質修復（降噪+補細節）開關 |
| `quality_strength` | int | 35 | 0–100 | 畫質修復強度（只有開關開啟才有效果） |
| `use_sharpen` | bool | true | — | 銳化開關 |
| `upscale_2x` | bool | false | — | 2 倍放大，**只在 `/render` 有效，`/preview` 忽略其視覺效果** |

> **重要**：每次呼叫 `/preview` 或 `/render` 都要送出**完整的參數物件**，後端沒有「只送差異值、其餘沿用上次」的合併邏輯——`EnhanceParams` 每個欄位都有預設值，若前端漏送某欄位，該欄位會回退成上表預設值，而不是「維持使用者上次設定的值」。前端必須自行在本地保存完整的目前參數狀態。

### Output（後端會回傳）

- **3.1** `POST /api/images` → JSON：`image_id`, `width`, `height`, `detected_mode`, `detected_label`, `detected_strength`
- **3.2** `GET /original` → `image/png` binary（縮圖版原圖）
- **3.3** `POST /preview` → `image/png` binary（縮圖版修復結果）
- **3.4** `POST /render` → `image/png` binary（原始解析度或 2× 修復結果）
- **3.5** `GET /api/capabilities` → JSON：`{"superres": bool}`
- 所有錯誤回應 → JSON：`{"detail": "<中文錯誤訊息>"}`（400/404/413），或 FastAPI 標準 422 驗證錯誤結構（422）

### Display（應該顯示給使用者）

- 修復前 / 修復後圖片
- 偵測到的偏色類型與強度
- 目前所有可調參數的數值/開關狀態
- 圖片原始尺寸（`width` × `height`），用於讓使用者理解「輸出 2× 後會是多大」
- 是否支援真的 AI 放大（來自 3.5，非必須顯示模型細節，但應反映在「放大選項的說明文字」上）
- 各種錯誤訊息（後端 `detail` 文字）

### Hidden（前端內部使用，不應直接暴露給使用者）

- `image_id`：技術性識別碼，不需要顯示在畫面上讓使用者看到或輸入。
- 內部參數運算細節：例如 `auto` 模式下實際套用的 `_auto_strength` / `_auto_preserve_stage_light` 調整後數值——後端**不會**把這些「自動微調後的實際生效值」回傳給前端，前端只能拿到自己送出的原始參數與最終圖片結果，看不到 auto 模式內部到底把 strength 動態調成多少。**這點請標記為「需要確認」**：如果新前端想呈現「auto 模式實際套用了多強的修正」，目前後端沒有提供這個資訊。

## 10. Authentication & Permission Requirements

**完全沒有身分驗證與權限機制。**

- 沒有登入、註冊、Token、Cookie、Session Cookie（`image_id` 不是身分憑證，只是資源識別碼，且沒有搭配任何驗證）。

- 新前端**不需要**設計任何登入/註冊畫面或流程。

## 11. Backend API Contract

> 以下為**不應更動**的實際契約內容，供新前端直接對接。

### `POST /api/images`
- Content-Type: `multipart/form-data`
- Body: `file`（必填）
- 200 回應 JSON：
  ```json
  {
    "image_id": "string",
    "width": 0,
    "height": 0,
    "detected_mode": "auto|purple|yellow|red|cyan|low_light",
    "detected_label": "string",
    "detected_strength": 0
  }
  ```
- 錯誤：400（空檔/無法解析）、413（超過 20MB）

### `GET /api/images/{image_id}/original`
- 200 回應：`image/png` binary
- 404：`{"detail": "圖片工作階段已過期，請重新上傳。"}`

### `POST /api/images/{image_id}/preview`
- Content-Type: `application/json`
- Body：完整 `EnhanceParams`（見第 9 節）
- 200 回應：`image/png` binary
- 404：同上；400：mode 不合法或 `ValueError`；422：欄位驗證失敗

### `POST /api/images/{image_id}/render`
- Content-Type: `application/json`
- Body：完整 `EnhanceParams`
- 200 回應：`image/png` binary（原始解析度，`upscale_2x=true` 時為 2 倍寬高）
- 錯誤同上

### `GET /api/capabilities`
- 200 回應：`{"superres": true|false}`

### 其他
- `GET /api/docs`：Swagger UI（FastAPI 自動生成）
- `GET /api/openapi.json`：OpenAPI schema
- `GET /`：回傳 `web/index.html`（目前作法；新前端若換掉這個檔案，這個路由的行為理論上不變，只是回傳的檔案內容不同）
- 其餘路徑由 `StaticFiles` 掛載在 `/`，會直接對應 `web/` 目錄下的實體檔案

## 12. Non-negotiable Technical Constraints

1. **Endpoint 路徑與 HTTP method** 不可更動：`POST /api/images`、`GET /api/images/{id}/original`、`POST /api/images/{id}/preview`、`POST /api/images/{id}/render`、`GET /api/capabilities`。
2. **上傳欄位名稱固定為 `file`**，且必須是 `multipart/form-data`。
3. **`EnhanceParams` 的欄位名稱、型別、預設值、範圍**必須照第 9 節表格，不可自行增減或改名（除非同時修改後端）。
4. **每次 `/preview`、`/render` 都要送出完整參數物件**——沒有 partial update 語意。
5. **圖片輸出格式固定為 PNG**（`image/png`），不是 JPEG，下載檔名/副檔名前端要自己處理。
6. **`image_id` 由後端產生，前端不可自行指定**，且是不透明字串，前端不應該解析或依賴其格式。
7. **Session 30 分鐘 TTL、全站最多 24 個並行 session**，且無法延長或替換——前端必須能處理「操作到一半 session 突然消失」的情境（404）。
8. **`/preview` 永遠對縮圖（最長邊 1400px）運算、`/render` 永遠對原始解析度運算**——這是刻意的效能設計（見 `api.py` 注解），前端不應假設兩者輸出像素完全一致，尤其是雜訊自適應演算法（`restore_image_quality`）在不同解析度下判斷出的雜訊量可能不同，兩者的視覺效果**可能有些微差異**，這是已知且刻意的行為，不是 bug。
9. **`upscale_2x` 對 `/preview` 沒有效果**，只在 `/render` 生效。
10. **超解析度模型的可用性完全由後端環境決定**，前端無法強制使用或停用「真的 AI 放大」——`upscale_2x=true` 永遠會成功，只是品質依環境而定（FSRCNN 或 Lanczos 降級）。
11. **沒有任何驗證機制**，不可假設有 Token/Cookie/Session 驗證可用，也不應該在前端加上假的登入畫面。
12. **沒有資料庫、沒有持久化**，不可假設重新整理頁面後還能拿回之前的 `image_id` 或參數（除非前端自己用 localStorage 等方式在前端保存 `image_id` 與參數，但即使保存了，後端 session 仍可能已過期）。

## 13. Recommended Frontend Requirements

> 這節是根據以上分析，對「新前端至少要滿足什麼」的建議，**不涉及視覺設計**。

1. 前端必須自行維護「目前完整參數狀態」的單一真實來源（因為後端無合併語意），每次呼叫 preview/render 都送出完整物件。
2. 必須明確區分「預覽中」與「輸出中」兩種等待狀態的訊息文案，讓使用者理解輸出通常要等更久。
3. 必須妥善處理 404（session 過期）為獨立的錯誤類型，而不是與 400/422 混在一起顯示同一種「發生錯誤」訊息——因為它的解法（必須重新上傳）跟其他錯誤（可以直接重試）不同。
4. 必須告知使用者「預覽畫質 ≠ 下載畫質」，尤其 `upscale_2x` 開啟時預覽不會變化。
5. 應在頁面載入或上傳前就查詢 `/api/capabilities`，以便誠實呈現放大選項的預期效果，而不是等使用者下載完才發現用的是插值不是 AI 模型。
6. 因為後端沒有進度回報，前端不應該編造假的進度百分比；如果想要更好的等待體感，應該用不定態（indeterminate）指示，而不是虛構數字。
7. 應該用防抖或節流處理連續的參數調整（例如拖動滑桿），避免對 `/preview` 發出過量請求——這是純前端效能考量，後端沒有限流機制會直接接受所有請求。
8. 下載檔名、格式轉換（若未來要支援 PNG 以外格式）需要在前端處理，後端固定只給 PNG。

## 14. Open Questions / Unclear Areas

以下事項**無法單純從現有後端程式碼確認**，標記為「需要確認」，設計新前端前建議先釐清：

1. **需要確認**：`auto` 模式下，後端內部依偵測到的偏色嚴重程度動態調整過的「實際生效強度」，是否需要暴露給使用者？目前 API 不回傳這個中間值。
2. **需要確認**：session 30 分鐘 TTL 與全站 24 個並行上限，是否為刻意的產品限制（例如展示用途、避免濫用），還是純技術妥協、之後可能會加大或改成資料庫持久化？這會影響前端要不要做「本地暫存以便 session 過期後快速復原」這類體驗補強。
3. **需要確認**：目前沒有任何端點能查詢「這個 session 還剩多久過期」，如果產品上希望在使用者編輯到一半時提醒「即將逾時」，後端需要新增對應資訊，目前無法在不改後端的情況下實現。
4. **需要確認**：是否預期未來會加上多圖 / 批次上傳？目前架構（單一 `image_id` 對應單一 session）並未設計成支援批次，若這是規劃中的方向，會影響新前端的資料模型設計，但不屬於目前後端契約範圍。
5. **需要確認**：`GET /api/capabilities` 目前只回報 `superres` 一項，未來若新增其他可選能力（例如更多修復模式），前端是否應該預期這個物件的欄位會增加？（純架構彈性問題，非阻塞項目。）
